前天晚上，我把一个折腾了一个多月的个人项目推上了 GitHub。

仓库叫 keel-agent，中文名龙骨。推完时，star 数是 0，fork 数是 0，watcher 是我自己。

按开源项目的标准，这个首发数据确实不好看。但我很满意，因为发布前那两天补了测试、写了验证记录，把十几个只有真机才能暴露的问题逐个解决了。

这个项目要回答一个问题：coding agent 这么多了，为什么还要自己再写一个？

答案很简单：因为现有的 agent 不会说「不」。

你让 agent 修个 bug，它改文件、跑命令，然后告诉你已经修复完成。你一跑测试，失败。

模型说完成和实际完成之间有巨大差距。

交互式场景还能接受，发现问题可以重新修改。但在 CI 里，在自动化代码维护里，这就致命了。流水线需要可靠的信号，不是一句口头承诺。

keel 就是解决这个问题的。它是一个 coding agent harness，核心是三个约定。

第一个约定：会话即事件流。

keel 的会话是一条只能追加的事件日志，一个 jsonl 文件。LLM 的每次请求响应、每次策略判定、每次工具调用、每份验证证据，全部作为带序号的事件写入。对话历史、花费、会话状态都是对这条日志做纯推导得到的视图。上下文压缩只是换视图，日志本身不变。

这条日志衍生出三个命令：replay 只读回放完整执行轨迹，每一步的判定和成本都可见；fork 从任意事件分叉出新会话；cost 按模型按回合生成账单，精确到每次调用。

第二个约定：证据驱动的完成契约。

只要会话使用了可能改文件的工具，模型想宣布完成就必须先调用 verify 跑验证，测试或构建通过的证据落盘存档。没有验证就想结束，打回，最多两次。还拿不出证据，以未验证状态结束，退出码 3。

退出码是给 CI 的。流水线不关心模型说了什么，只认 0 还是 3。完成不是语气，是可以写进 shell 脚本的数字。

第三个约定：策略先行。

所有工具调用先经过声明式策略引擎再执行。路径黑名单拦截 .env 和私钥的读写，命令黑名单、人工审批、只读模式、会话花费超预算自动熔断。每个判定本身也作为事件记录，审计时可以看到每次放行和拒绝的理由。

最后是零运行时依赖。整个项目三千七百行 TypeScript，npm 安装后没有运行时依赖。支持三种线协议：OpenAI、Anthropic、Responses。环境里 export 了哪家的 key 就用哪家，没有 key 的话，KEEL_MOCK=1 可以用内置的确定性 mock 模型跑通全流程。

前段时间研究了 Apache 孵化器里的 Maka 项目。Apache Maka，孵化中，五千七百颗星，定位是高性能 agent workspace。README 里有句话：保存着它做过的一切事情的完整记录。

![Apache Maka 的 GitHub 主页](/assets/post_imgs/2026-10-04-keel-agent/github-maka.png)

它的设计哲学一行字：The log is the runtime。

日志即运行时。每个模型消息、每次工具调用、每个权限决定、每次终止，都是只能追加的 RuntimeEvent。界面、下一轮 prompt、崩溃恢复都是这条日志的投影。

这就是 keel 的思路。

那条 events.jsonl，纯推导的视图，fork 和 replay——和一个在 Apache 孵化器里有近五千个 commit 的项目，在同一个地方做了同样的判断：agent 运行时的真相源应该是那条只能追加的日志。

![keel-agent 的 GitHub 主页](/assets/post_imgs/2026-10-04-keel-agent/github-keel-agent.png)

两个独立的团队收敛到同一个设计，说明这条路径的共识已经形成，剩下的是谁在哪个场景把它做透。

差别也很明显。

Maka 是完整的工作区，桌面端、终端、CLI、评测，全部是同一个执行核心的瘦客户端。它证明自己的方式是跑分，README 里说：我们发布每一次运行，同样的模型、同样的官方验收器、完整的逐任务记录。把 harness 的好坏变成一张公开的成绩单。

keel 的方向不同。它不想成为工作区，只想确保一次任务的可信完成。证明方式不是跑分，是运行时契约——会话的每次完成都必须有当场落盘的验证证据，否则退出码直接告诉 CI 未完成。

一个管统计，一个管个案。一个给平均分，一个要求当场验货。不冲突，反而互补。

现实一点说。

keel 现在是 0.3.0，仓库里有验证记录，七十六个测试全绿，step-5-preview 真实模型的全链路验证也通过了。但文档里明确写着：当前证据只支持受控试运行。翻译一下，我自己敢用它跑小任务，不敢放进任何生产流水线。

0 star 的仓库说这话反而轻松。

接下来的方向分两层。

keel 这层，三个方向。一是把完成契约打磨到敢默认开启，fork 之后证据失效、子进程清理这些边界已经补了回归，还需要真实负载检验。二是学 Maka 的评测文化，harness 不跑分就没有话语权，我想把 keel 放进公开基准里跟同行比。三是把 fork 用起来，CI 里的重试不该从头开始，应该从失败事件分叉，省 token 还能做归因。

我自己这层是更大的计划。Maka 是我今年主攻的 Apache 项目，从提 PR 做起。keel 对我来说除了项目本身，还是练兵场。自己从头写过 harness 的人，才知道崩溃恢复为什么要区分已提交和未提交的日志，才知道 fork 为什么不能回滚工作目录，才知道一个退出码背后要处理多少种中断。知道这些之后，给 Maka 提的每个建议才能落在点上。

keel 把地基打实，Maka 那边的路会越走越宽。

十五世纪的威尼斯商人发明了复式记账法。每笔交易记两遍，借贷相等，账本对不上就有问题。这套方法用了六百年，成了现代商业文明的信任基础。

agent 时代需要同样的方法。模型会幻觉，会遗忘，会打包票，所以它的每个动作都要记两遍：一遍进日志，一遍进证据，两边对得上才算数。

日志是账本，证据是签收单，退出码是信用分。

之前写记忆那篇提到，你记得什么，你就是谁。这篇补一句：你怎么记账，别人就怎么信你。

keel 在 GitHub 上，叫 keel-agent，MIT 协议。零依赖安装，没有 API key 也能试，KEEL_MOCK=1 一个环境变量，事件溯源、验证契约、回放分叉全流程都能体验，不花钱。

0 star 的项目，你就是第一个用户。
