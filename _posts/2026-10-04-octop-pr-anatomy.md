九月十九号深夜，提了给 Octop 的第一个 PR。

起因很简单。删除对话线程时，绑定在线程上的会话没有级联删除，变成了悬空数据。这个 bug 不会报错，只会导致历史记录悄悄丢失，直到命令行工具因为断言失败而崩溃。

顺着崩溃栈找到问题所在。会话仓库层缺少级联删除逻辑，读会话的路径也需要加兜底重绑。一个多小时修完提交。

到今天，在 Octop 主仓提了二十个 PR。九个合并，五个关闭，六个待审，外加底层运行时 harness 里一个。这篇文章按类型梳理这二十个 PR，记录一个普通贡献者在六千星项目里的经历。

![我在 Octop 的全部 PR 列表，按创建时间排序](/assets/post_imgs/2026-10-04-octop-prs/pr-list.png)

## 按改动规模分类

### 最小改动

最小的一个改了一行 CSS。Octop 暗色模式缺少一个设计变量定义，知识库预览在暗色主题下背景全白。补了变量，二十分钟合并。借这个 PR 了解了项目的发版节奏和 review 风格。

### 小问题修复

接下来是一批小问题。缺失的设计 token、双语翻译键、AI 生成图片的内联预览缺少沙箱隔离、备份导入会覆盖内置技能，这些问题都是使用过程中自然暴露出来的。九月二十七号提了四个，那行 CSS 就是其中之一。

### 安全问题

再往上是安全问题。悬空会话 PR 合并后，在重构频道连接时发现 OAuth 回调存在漏洞。用户保存的跳转地址直接插入脚本，提供商的错误信息直接插入 HTML，存在存储型 XSS 和开放重定向风险。

修复方案是复用现有的 SSO 重定向校验，拒绝外站、反斜杠和浏览器解析前会移除的控制字符（包括用换行绕过域名校验的情况）。弹窗通信不再用通配符，一并补充了回归测试。这个修复进了 1.0.2 的版本说明。

![OAuth 回调安全修复的 PR 页](/assets/post_imgs/2026-10-04-octop-prs/pr-942.png)

### 多 agent 协作问题

下一个修复的是多 agent 协作中的隐蔽问题。

当目标 agent 的模型重试耗尽时，底层默认返回一条空消息。后台收件箱收到消息后标记为完成。任务实际失败了，但系统认为成功。

错误不会扩散，假的成功会。派发任务的 agent 拿着空结果继续执行，后续节点都在基于一个不存在的成功工作，发现问题时已经隔了好几个环节。

这个 PR 修改了失败的表达方式。重试耗尽时抛出错误，让收件箱标记为 failed，并将错误传回给派发方。改动涉及框架的多个下游模块。

### 功能实现

再往上是第一个完整的功能实现。

有个 issue 提议让专家可以配置默认对话模式。先调研了现状，写了份 PRD。结论先行，现状列举十条并精确到代码行号，后端和前端各列出四个方案，标注风险和开放问题。然后按照 PRD 实现，涉及十二个文件，加九十三行删七行，四天后合并。

![从 issue 到 PRD 到实现，一圈完整走完](/assets/post_imgs/2026-10-04-octop-prs/pr-1338.png)

这个 PR 不大，但流程完整：方案在评审前就写清楚，存储复用现有配置通道，无需迁移。

## 被关闭的 PR

接下来说被关闭的五个 PR。

团队后台回复的 PR，上游后来用另一种方案实现了，主持人改写派工的方案更优雅，关闭了自己的。定时任务时区的也是类似情况，被上游更好的实现覆盖。还有一个被关闭时核心改动确实合并进去了，只是压到了别人的提交里。内容保留了，但提交记录没有署名。

另外两个关闭后又重开了。同 agent 重载串行化和上下文用量统计，第一次提交被关闭，但看了合并进上游的处理后认为没有完全修复，重新开了新 PR 继续讨论。这两个现在还在审查中。

底层运行时的 thinking 分块修复，是自己修的 bug 在本地测试时又出现了新问题，昨天凌晨处理的。

## 最大的 PR

目前最大的一个还在审查中。

官方 issue 里有人一直想要 Agent Mail 功能，让 agent 能收发邮件。十月三号提交了实现，三十八个文件，两千四百多行。包括设备码授权、十一个邮件和附件工具、邮箱按实例隔离。五种写操作需要先预览再执行，通过一次性令牌确认，五分钟过期。新邮件通过官方接口的长连接触发定时任务，空闲时不调用模型。

![Agent Mail 大功能 PR，还在等 review](/assets/post_imgs/2026-10-04-octop-prs/pr-1573.png)

邮件工具的风险和查询资料不同，发出的邮件无法撤回，所以预览、令牌、过期这套流程不能省。

这个 PR 现在还没有评论，维护者还没开始 review。可能会被拒绝，可能需要大改，也可能某天出现在版本说明里。

## 总结

两周，二十个 PR。每个都来自实际使用中遇到的问题。能一行解决的不重构，安全修复的描述写得比代码还详细，被关闭的复盘原因，重开的继续跟进。第一次提 PR 前反复检查了很久，合并几个之后就顺手多了。

八月底那篇秋招文章提到，企业更信可回溯的记录。这二十个 PR 带着讨论、评审和版本号，就是这样的记录。
